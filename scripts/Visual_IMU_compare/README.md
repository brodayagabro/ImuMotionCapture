# Оптический захват движений: запись SkellyCam → FreeMoCap → BVH

Основной режим этого эксперимента — **запись на отдельных компьютерах с камерами,
передача готовых файлов на хост, синхронизация по общей вспышке, штатная
постобработка FreeMoCap и экспорт BVH через Blender**. В веб-интерфейсе можно
выбрать папку/имя итогового BVH, скачать его и проиграть запись на прежней
WebGL-арматуре с паузой, перемоткой и изменением скорости.

Каталоги сохранены: `camera/` — узел камеры, `server/` — хост, `src/` —
существующий семафорный эксперимент. Старый режим RTSP остаётся доступен;
его инструкции находятся ниже, в разделе «Прежний режим».

```text
192.168.1.98  · cam1 · SkellyCam → локальный MP4 + временные метки ─┐
192.168.1.112 · cam2 · SkellyCam → локальный MP4 + временные метки ─┼→ хост
                                                               │
                   управление/получение файлов по HTTP :8082 ←──┘
хост :8080 → SkellySync → FreeMoCap MediaPipe → 3D/фильтрация → Blender → BVH
                       └→ веб-интерфейс: папка результата, журнал, проигрыватель
```

Это **синхронизация записей после захвата**, не аппаратный одновременный запуск
экспозиции. SkellyCam на разных компьютерах сам по себе не создаёт общие часы
камер. Общая вспышка совмещает начало временных шкал с точностью до кадра;
одна вспышка не измеряет дрейф частоты за длинную запись. Начните с дублей
10–30 секунд и одинаковых FPS. Для измерений точности синхронизации на всём
интервале сохранён [LED-бенчмарк](server/SYNC_BENCHMARK.md).

## 1. Клонирование на каждом компьютере

```bash
git clone https://github.com/brodayagabro/ImuMotionCapture.git
cd ImuMotionCapture/scripts/Visual_IMU_compare
```

Для существующего чистого клона: `git pull --ff-only` из корня репозитория.
Никаких путей к `equipment/VisualMoCap` и ранее созданным окружениям не нужно.
Первичная установка требует интернета. Исходники зависимостей загружаются
в локальные `repositories/`, окружения — в `.venv-*`; они исключены из Git.

## 2. Обе камеры: установка

Выполнить на **192.168.1.98** и **192.168.1.112**:

```bash
cd camera
bash setup.sh --workflow recording --system-deps
v4l2-ctl --list-devices
ls -l /dev/v4l/by-id/
v4l2-ctl --device /dev/video0 --list-formats-ext
```

Окружение: **camera/.venv-skellycam**, Python 3.12, штатный SkellyCam.
Для этого режима нужен 64-битный Linux с V4L2. Настройка проверена на x86_64;
на ARM64 доступность всех закреплённых колёс нужно проверить установкой.

`--system-deps` — единственная часть setup, использующая sudo: устанавливает
`python3-venv`, Git, FFmpeg **вместе с ffprobe**, `libgl1`, `libglib2.0-0`,
`libportaudio2`, `v4l-utils`. PortAudio нужен для импорта SkellyCam, даже если
звук не записывается. Если эти пакеты уже есть, убрать `--system-deps`:

```bash
bash setup.sh --workflow recording
```

Не запускайте весь setup от root. Для доступа к камере пользователь должен
состоять в группе `video`: при необходимости `sudo usermod -aG video "$USER"`,
после чего выйти из сессии и войти снова.

## 3. Запуск узлов камеры

Сначала остановить прежний `camera_streamer.py`, если он использует эту же
камеру. Для ранее установленного сервиса: `sudo systemctl stop
visual-mocap-camera-cam1.service` (на второй камере — `cam2`). Для постоянного
перехода можно также отключить его автозапуск через `systemctl disable`.
`install_service.py` пока относится к прежнему RTSP-режиму.

На **192.168.1.98**, из `camera/`:

```bash
.venv-skellycam/bin/python skellycam_node.py \
  --name cam1 --device /dev/video0 --resolution 1280x720 --fps 30 \
  --host 0.0.0.0 --port 8082
```

На **192.168.1.112**, из `camera/`:

```bash
.venv-skellycam/bin/python skellycam_node.py \
  --name cam2 --device /dev/video0 --resolution 1280x720 --fps 30 \
  --host 0.0.0.0 --port 8082
```

Можно поставить `--resolution 640x480 --fps 30` для первого теста. Используйте
режим, который действительно поддерживают обе камеры. Вместо `/dev/video0`
лучше указать полный постоянный путь `/dev/v4l/by-id/...-video-index0`:
номер устройства определяется при открытии камеры. После переподключения
перезапустите узел. Дополнительно: `--capture-fourcc MJPG|YUYV`,
`--exposure-mode AUTO|MANUAL`, `--exposure -7`.

Серверу не нужно указывать IP хоста в командах камеры: он сам обращается к
двум HTTP-узлам. Камера открывается после команды записи с веб-страницы.
Локальные видео остаются в `camera/runtime/records/`; каталог можно изменить
через `--records /путь/к/записям`. Для завершения узла — Ctrl+C.

Если UFW включён, **на обеих камерах**:

```bash
sudo ufw allow from 192.168.1.0/24 to any port 8082 proto tcp
```

## 4. Хост: установка и запуск

Из `scripts/Visual_IMU_compare/server`:

```bash
bash setup.sh --workflow recording --system-deps
.venv-freemocap/bin/python freemocap_host.py \
  --camera cam1=http://192.168.1.98:8082 \
  --camera cam2=http://192.168.1.112:8082 \
  --host 0.0.0.0 --port 8080
```

`--system-deps` здесь дополнительно устанавливает Blender. Если системные
пакеты уже есть, этот флаг не нужен. Проверить: `ffmpeg -version`,
`ffprobe -version`, `blender --version`. Для Blender из другого каталога:
`--blender /полный/путь/blender`. Проверен Blender 4.0.2 из Ubuntu 24.04.

Окружение: **server/.venv-freemocap**. Используется закреплённый FreeMoCap
**v2.0.0-alpha.25**, SkellyCam **v2.0.0-alpha.6** и их штатные компоненты.
В этом закреплённом FreeMoCap экспорт Blender/BVH поддерживает **MediaPipe**;
RTMPose для этого экспорта upstream пока отклоняет. Поэтому здесь MediaPipe
с готовыми весами, **инференс на CPU**, без обучения. Наличие RTX 5090 не
меняет этот выбранный путь. Веса тела, рук и лица автоматически скачиваются
при первой обработке движения в штатный `~/.freemocap/skellytracker-models`.
Первый запуск обработки поэтому дольше следующих.

Открыть:

- для теста на нынешнем компьютере: **http://192.168.1.54:8080**;
- после переноса на GPU-сервер: **http://192.168.1.90:8080**.

Если UFW включён, **на хосте**:

```bash
sudo ufw allow from 192.168.1.0/24 to any port 8080 proto tcp
```

Порт 8554 и `rtsp_relay.py` для нового режима не нужны. Если прежний веб-сервер
занимает 8080, остановить его или выбрать другой `--port`. HTTP-управление
рассчитано на доверенную локальную сеть, авторизация не включена.

## 5. Проверка светодиодом

1. Выбрать «Проверка синхронизации» и нажать «Начать запись».
2. Дождаться надписи **«Все камеры записывают — можно дать вспышку»**.
3. До этого момента светодиод должен быть выключен. Дать **одну общую яркую
   вспышку на 100–200 мс**, видимую обеим камерам. Лучше освещать ею заметную
   часть сцены или рассеиватель: SkellySync измеряет среднюю яркость всего
   кадра, маленькая точка может не пройти порог.
4. Записать ещё несколько секунд и нажать «Остановить и обработать».
5. Дождаться «Готово», открыть «Отчёт синхронизации»: `lags` — сколько секунд
   удалено с начала каждого файла, `aligned_flash_frames` — кадры вспышки
   **после** обработки. Разница должна быть не более одного кадра.

Не включайте регулярное мигание до начала записи всех камер: разные узлы
могут выбрать разные импульсы. Порог по умолчанию — 1000, он настраивается
в «Доска и вспышка». Уменьшение порога делает возможным ложное срабатывание
на движения/автоэкспозицию. Отчёт проверяет выбранное событие, а не доказывает
аппаратную синхронность или отсутствие дрейфа. Исходники не удаляются.

## 6. Калибровка, движение, сохранение и воспроизведение

1. Выбрать «Калибровка ChArUco». В «Доска и вспышка» **указать реальные**
   количества квадратов, размер квадрата в мм, отношение маркера к квадрату
   и словарь ArUco. По умолчанию стоит штатная доска FreeMoCap 5×3, 54 мм,
   отношение 0.8, `DICT_4X4_250`. Для прежней доски проекта могут требоваться
   **7×5, 40 мм, 0.8, `DICT_4X4_50`** — проверьте вашу распечатку!
2. Начать запись, дождаться готовности всех камер, дать вспышку. Затем 30–60
   секунд показывать жёсткую плоскую доску в разных положениях и наклонах
   по рабочему объёму, с одновременной видимостью в обеих камерах.
3. Остановить запись. Хост получает файлы с проверкой SHA-256, синхронизирует
   и запускает штатный `PosthocCalibrationPipelineConfig` / Anipose FreeMoCap.
   По завершении нажать «Использовать калибровку».
4. Выбрать «Захват движения → BVH». Камеры после калибровки не двигать, не
   менять их разрешение, фокус или зум. Человек должен быть целиком виден
   в обеих камерах, включая кисти и стопы.
5. Ввести папку **на файловой системе хоста** либо выбрать её кнопкой
   «Выбрать»; задать имя вроде `semaphore_001.bvh`. Каталог создаётся, если
   его ещё нет. Уже существующий итоговый BVH не перезаписывается.
6. Начать запись, дать вспышку после готовности всех камер, выполнить движение,
   остановить. Дождаться детекции, триангуляции, фильтрации и экспорта Blender.
7. Нажать «Проиграть»: доступны пауза, перемотка, повтор, скорость 0.5×/1×/2×,
   вращение и масштабирование WebGL-арматуры. «Скачать BVH» сохраняет файл
   на компьютер с браузером. В проигрывателе используются кости и каналы
   самого BVH, нарисованные теми же восьмигранными костями, что в прежнем UI.
   Для дополнительной копии поменять папку/имя слева и нажать
   «Сохранить BVH в выбранную папку» у готового дубля.

Старый `calibration.json` сервера RTSP здесь **не используется**. Нужен
штатный `.toml` FreeMoCap с теми же camera ID (`cam1`, `cam2`) и геометрией
камер. Путь к внешнему готовому `.toml` можно ввести вручную.

## Данные, диагностика и воспроизводимость

Хост сохраняет сессии по умолчанию в `records/freemocap/<id>/`, итоговый BVH
— в выбранную папку (по умолчанию `output/`). Переопределение при запуске:
`--records /data/takes --output /data/bvh`. Внутри сессии сохраняются:

- `camera_files/` — исходные файлы и временные метки SkellyCam;
- `raw_videos/`, `synchronized_videos/` — исходные и совмещённые видео;
- `transfer_manifests.json`, `flash_evidence.json`, `sync_result.json` — проверки;
- `synchronized_videos/timestamps/` — производная равномерная временная шкала
  готовых видео с отметкой происхождения, для FPS фильтров и Blender;
- `output_data/`, `3d_models/`, `.blend` — результаты штатной обработки;
- `take.json`, `spec.json`, `progress.json`, `worker.log` — параметры и журнал.

Видео сохраняются и после успеха, и после ошибки — для проверки и повторной
обработки. Удалять ненужные сессии нужно вручную **на хосте и на камерах**.
После перезапуска хоста незавершённая сессия помечается «Прервано»; кнопка
повторного получения/обработки использует прежние ID, проверяет контрольные
суммы и не требует нового дубля, если узлы сохранили финализированные файлы.
После аварии самого узла незакрытый файл нельзя считать готовым: смотрите его
журнал. Кнопка «Журнал» на хосте показывает ошибку native worker.

Закрепления — `camera/requirements-recording-repositories.txt`,
`server/requirements-recording-repositories.txt` и `uv.lock` внутри выбранных
коммитов. Отдельные совместимые версии хоста — `server/requirements-recording.txt`.
Исправления совместимости в нашей обвязке документированы в
[server/README.md](server/README.md#режим-записи-skellycam--freemocap).

Проверки нового режима:

```bash
bash server/setup.sh --workflow recording --with-tests
server/.venv-freemocap/bin/python -m pytest server/test_recording_workflow.py -q
node server/test_bvh_player.cjs
```

На тестовых данных проверены native-калибровка (ошибка репроекции около
0.11 px), полный проход двух видео через синхронизацию, MediaPipe, 3D,
постобработку и Blender/BVH, а также браузерное воспроизведение. Это проверки
на синтетической геометрии/проецируемом изображении; качество и реальная
синхронность двух ваших камер ещё должны быть проверены физическим тестом.

`node` нужен только для теста BVH-проигрывателя, не для запуска приложения.
Автотесты с генерируемыми видео не заменяют проверку ваших реальных камер.

## Прежний режим: RTSP, захват в реальном времени и семафорный эксперимент

Следующие команды относятся к `camera_streamer.py` / `visual_mocap_server.py`,
а не к описанному выше режиму записи SkellyCam.


| Компьютер | Каталог | Назначение |
|---|---|---|
| Компьютер/одноплатник с камерой | [camera/](camera/README.md) | V4L2 → H.264 → RTSP |
| Хост-сервер | [server/](server/README.md) | Приём RTSP, RTMPose, 3D, WebGL, BVH |
| Компьютер оператора эксперимента | [src/](src/README.md) | IMU + визуальный BVH, OpenGL, семафор, парная запись |

Семафорный эксперимент по сценарию ER2026 перенесён в **[src/](src/README.md)**.
Он получает BVH от видеосервера вместо Noitom и сохраняет `custom.bvh` / `visual.bvh`.
Запуск: `python scripts/Visual_IMU_compare/src/main.py --source-ip 192.168.1.90`
из корня клона, в окружении настольного приложения (`src/setup.sh`).

```text
Камера 1 → camera_streamer.py ─┐
Камера 2 → camera_streamer.py ─┼→ MediaMTX → visual_mocap_server.py → WebGL / BVH
Камера 3 → camera_streamer.py ─┘   rtsp_relay.py     RTMPose + FreeMoCap DLT
```

На каждом компьютере нужен **только этот репозиторий**. Установщики сами
получают пакеты, исходники, модели и бинарники. Пути к ранее склонированному
`MotionCapture/equipment/VisualMoCap` не нужны. Первое развёртывание требует
интернета. Серверу нужен полный клон ImuMotionCapture: он использует также
`host/storage/bvh.py` из этого же репозитория.

## Клонирование

```bash
git clone https://github.com/brodayagabro/ImuMotionCapture.git
cd ImuMotionCapture/scripts/Visual_IMU_compare
```

Далее выбрать роль. `--system-deps` устанавливает системные зависимости
через apt/sudo. Если они уже есть, этот флаг можно опустить.
Не запускайте весь setup через sudo: повышение прав используется только для apt.

## Компьютер с камерой

```bash
cd camera
./setup.sh --system-deps
source .venv/bin/activate
python camera_streamer.py --list-devices
python camera_streamer.py \
  --server 192.168.1.10 --name cam1 \
  --resolution 1280x720 --fps 30
```

Заменить IP адресом хост-сервера. На остальных компьютерах использовать
`cam2`, `cam3`. Если камер несколько, добавить `--device /dev/videoN`;
единственная камера выбирается автоматически.

Поддерживаемые разрешения и FPS: `python camera_streamer.py --list-formats`
(при необходимости добавить `--device /dev/videoN`).
[Таблица режимов C920 и подробности](camera/README.md#доступные-разрешения-и-fps).

Для проверки ракурса добавить к команде камеры `--preview` и открыть
`http://IP_КОМПЬЮТЕРА_С_КАМЕРОЙ:8081/`. RTSP продолжает передаваться
на сервер; превью использует тот же захват камеры.

Для запуска камеры **сразу после включения компьютера**, из `camera/`:

```bash
.venv/bin/python install_service.py --install \
  --server 192.168.1.90 --name cam1 --device /dev/video0 \
  --resolution 1280x720 --fps 30 --preview
```

Предварительно остановить ручную трансляцию. Сервис работает без входа
пользователя, повторяет запуск при ошибке и использует это окружение.
[Настройка автозапуска и команды управления](camera/README.md#автозапуск-при-включении-компьютера).

Создаётся `camera/.venv`, проверяются FFmpeg/V4L2. Нейросети и CUDA
на компьютере с камерой не устанавливаются.
[Подробная инструкция камеры](camera/README.md).

## Хост-сервер

Для NVIDIA GPU с подходящим драйвером:

```bash
cd server
./setup.sh --system-deps --device cuda
source .venv-cuda/bin/activate
python rtsp_relay.py
```

Оставить ретранслятор работающим. Во втором терминале, также из `server/`:

```bash
source .venv-cuda/bin/activate
python visual_mocap_server.py \
  --device cuda:0 --host 0.0.0.0 --port 8080 \
  --camera 'cam1=rtsp://127.0.0.1:8554/cam1' \
  --camera 'cam2=rtsp://127.0.0.1:8554/cam2' \
  --bvh-target 192.168.1.20:7001
```

Открыть **http://IP_СЕРВЕРА:8080**. Указывать только запущенные камеры;
для третьей добавить `--camera cam3=rtsp://127.0.0.1:8554/cam3`.
`--bvh-target` задаёт адрес принимающего хоста; параметр можно опустить.

Для CPU вместо CUDA, из `server/`:

```bash
./setup.sh --device cpu
source .venv-cpu/bin/activate
python visual_mocap_server.py --demo --device cpu
```

`--demo` показывает синтетические камеры. Для реального захвата заменить
его параметрами `--camera`. Метрический 3D требует калибровки минимум двух
камер через веб-интерфейс.

Калибровка выполняется по видео: «Начать запись» → медленно перемещать
ChArUco-доску перед всеми камерами → «Остановить и калибровать».
Параметры камер рассчитывает штатный Anipose-калибратор FreeMoCap
с совместным уточнением камер (bundle adjustment).
Через 60 секунд запись остановится автоматически. Сервер сохранит результат
в `calibration.json` и удалит временные видео; при ошибке или отмене прежняя
калибровка сохраняется. Параметры записи — в [инструкции сервера](server/README.md#калибровка-и-синхронизация).

Серверный setup создаёт:

- `.venv-cpu/` или `.venv-cuda/` с закреплёнными Python-пакетами;
- `.venv-calibration/` для штатного калибратора, отдельно от CUDA/ONNX;
- `repositories/rtmlib`, `repositories/freemocap` и зависимости калибратора
  `skellycam`, `skellytracker`, `skellylogs` на закреплённых коммитах;
- `.tools/bin/mediamtx` с проверкой SHA-256;
- `.cache/rtmlib/` с готовыми моделями YOLOX-m и RTMPose-m.

Если системный Python слишком старый, setup автоматически получает приватный
Python 3.12 через закреплённый uv. Он остаётся внутри папки выбранной роли.
Для серверного профиля приватный Python 3.12 также используется, если системная
версия новее: это ограничение закреплённых зависимостей калибратора.
Драйвер NVIDIA установщик не меняет. Закреплённый ONNX Runtime GPU 1.31.1
использует CUDA 13.x: драйвер должен быть совместим. Jetson требует
согласования с JetPack. [Подробная инструкция сервера](server/README.md).

## Повторная установка и Git

Setup можно запускать повторно: проверяются окружения, пакеты и исходники.
Пользовательские изменения в локальных клонах не сбрасываются; при
несовпадении setup останавливается с диагностикой. Камеры и постоянные
сервисы во время установки не запускаются.
`server/setup.sh --skip-models` откладывает загрузку моделей до первого запуска.
`--with-tests` добавляет зависимости для тестов.

В Git хранятся **исходники, setup.sh, requirements-файлы, тесты и документация**.
Окружения `.venv*`/`.env*`, `.tools`, `.cache`, `repositories` и `runtime`
исключены через `.gitignore`. Фактические версии установленных пакетов
сохраняются локально в `runtime/requirements-resolved*.txt`.

Прежнее `.venv-visual-cpu` в корне эксперимента сохранено как локальная
резервная установка. Новые команды его не используют. Окружения не копируются
на другие компьютеры: на каждом клоне запускается setup.
