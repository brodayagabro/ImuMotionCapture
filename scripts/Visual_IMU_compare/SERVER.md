# Сервер визуального захвата

Приложение: [`visual_mocap_server.py`](visual_mocap_server.py).
Python, HTML, JavaScript и WebGL находятся в одном файле. Отдельная сборка
frontend, CDN и настольный GUI FreeMoCap не нужны.

Отправитель для Ubuntu/Debian: [camera_streamer.py](camera_streamer.py).
Он публикует видео на IP сервера через RTSP; настройка MediaMTX и команды
для обеих сторон приведены в [CAMERA_STREAMER.md](CAMERA_STREAMER.md).

## Выбранная модель и зависимости

**RTMPose-m + YOLOX-m**, preset `balanced`, COCO-17, ONNX Runtime.
Используются готовые веса: обучение не требуется. Можно выбрать
`--preset lightweight` или `--preset performance`; это меняет готовые
модели и размеры их входа. Это не оценка точности на нашей установке.

Код загружается из уже склонированных репозиториев:

- `MotionCapture/equipment/VisualMoCap/rtmlib` — детектор, RTMPose,
  предобработка, постобработка и получение весов;
- `MotionCapture/equipment/VisualMoCap/freemocap` — DLT-триангуляция;
- `ImuMotionCapture/host/storage/bvh.py` — преобразование вращений в BVH-каналы.

Программа ищет каталог `equipment/VisualMoCap` относительно своего расположения.
На другом сервере можно передать `--repos /path/to/VisualMoCap`.
Основные библиотеки устанавливаются в отдельное окружение через `--setup`.
RTMlib импортируется из клона: его pip-зависимости не устанавливаются
автоматически, чтобы не смешивать CPU/GPU ONNX Runtime и несколько OpenCV.
Исходники внешних репозиториев не изменяются.

## Быстрая проверка

Все команды ниже выполняются из `ImuMotionCapture/scripts/Visual_IMU_compare`.
Python должен быть версии 3.11 или новее; локально проверен Python 3.12.14.

```bash
python visual_mocap_server.py --setup cpu
.venv-visual-cpu/bin/python visual_mocap_server.py --demo --device cpu
```

Открыть **http://127.0.0.1:8080**. Демонстрационный режим создаёт три
синтетических видеопотока с известными проекциями движущегося скелета.
Он проверяет приём кадров, триангуляцию, WebSocket, WebGL и формирование BVH.
**Нейросеть в `--demo` не запускается**, что явно показано в интерфейсе.

Локальное окружение `.venv-visual-cpu` уже создано при разработке.
Повторный `--setup` не перезаписывает существующее окружение.
На Windows исполняемый файл находится в `Scripts/python.exe` вместо `bin/python`.

## GPU и RTSP

Для сервера с NVIDIA GPU:

```bash
python visual_mocap_server.py --setup cuda
.venv-visual-cuda/bin/python visual_mocap_server.py \
  --device cuda:0 --host 0.0.0.0 --port 8080 \
  --camera 'cam1=rtsp://192.168.1.101:8554/camera' \
  --camera 'cam2=rtsp://192.168.1.102:8554/camera' \
  --camera 'cam3=rtsp://192.168.1.103:8554/camera' \
  --calibration runtime/calibration.json \
  --bvh-target 192.168.1.10:7001 --bvh-transport udp \
  --bvh-file runtime/session_001.bvh
```

Открыть **http://IP_СЕРВЕРА:8080**. Программа по умолчанию слушает только
localhost; `--host 0.0.0.0` открывает доступ с других компьютеров.
Это сервис для доверенной локальной сети, без встроенной аутентификации.

`--setup cuda` устанавливает ONNX Runtime GPU и его CUDA/cuDNN-зависимости;
драйвер NVIDIA должен присутствовать на сервере. После создания обеих
нейросетевых сессий проверяется наличие `CUDAExecutionProvider`.
При неудачной инициализации GPU показывается ошибка; скрытого перехода
на CPU нет. `--device cpu` разрешает CPU явно. Требования драйвера и
библиотек зависят от установленного ONNX Runtime:
[официальная документация CUDA EP](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html).

При первом реальном запуске RTMlib скачивает готовые веса в свой кеш
`~/.cache/rtmlib/hub/checkpoints`. Можно задать локальные ONNX-файлы
через `--det-model` и `--pose-model`; они должны соответствовать выбранному
preset и 17-точечной модели. Для сервера без интернета веса нужно перенести заранее.

RTSP использует OpenCV/FFmpeg, по умолчанию TCP. Для UDP:
`--rtsp-transport udp`. Переменная `OPENCV_FFMPEG_CAPTURE_OPTIONS`, если
задана оператором, имеет приоритет. Декодирование видео выполняется на CPU;
на GPU выполняются детектор и RTMPose. Аппаратное декодирование не реализовано.

Каждая камера имеет отдельный поток чтения, ограниченный буфер последних
8 кадров, таймауты открытия/чтения и переподключение. Старые задания инференса
не накапливаются. Один экземпляр модели последовательно обрабатывает виды;
`--fps 20` ограничивает число полных циклов, а не обещает фактические 20 FPS.
Ускорение пакетным инференсом можно добавить после измерений на целевом GPU.

Вместо длинной командной строки можно использовать `--config runtime/cameras.json`:

```json
{
  "cameras": [
    {"id": "cam1", "source": "rtsp://192.168.1.101:8554/camera", "offset_ms": 0},
    {"id": "cam2", "source": "rtsp://192.168.1.102:8554/camera", "offset_ms": -12}
  ]
}
```

`offset_ms` прибавляется к серверному времени получения кадра; это ручная
компенсация измеренной постоянной задержки. USB-индекс и путь к видео также
допустимы как `source`. Файлы проигрываются с исходным FPS и повторяются.
Адреса камер не передаются браузеру; системные сообщения FFmpeg могут
содержать URL, поэтому логи с учётными данными следует хранить локально.

## Калибровка и синхронизация

Без калибровки работают видео и 2D-точки. Метрический 3D и BVH требуют
как минимум двух калиброванных камер.

1. Разместить камеры неподвижно, выставить рабочее разрешение и фокус.
2. Открыть «Калибровка камер» и скачать ChArUco-доску. По умолчанию это
   7×5 клеток, сторона клетки 40 мм, маркера 30 мм, `DICT_4X4_50`.
   Размеры можно изменить через `--board`, `--square-m`, `--marker-m`.
   При печати проверить линейкой именно клетку, исключив белые поля PNG.
3. Собрать минимум 12, лучше 20–30 разных положений и наклонов доски.
   Она должна покрывать разные области изображения, быть видна всем камерам
   и оставаться неподвижной во время каждого снимка.
4. Нажать «Вычислить и сохранить». Оцениваются intrinsics, дисторсия и
   extrinsics относительно первой камеры. Решение с RMS выше 3 px отклоняется.
5. Убрать доску и оставить одного человека в зоне общего обзора.

Калибровка сохраняется в `--calibration` и загружается при следующем запуске.
После перемещения камеры, изменения фокуса или разрешения её нужно повторить.
При несовпадении разрешения точки этой камеры исключаются из триангуляции.
Повторная калибровка создаёт новый BVH-stream ID; для нового файла записи
лучше перезапустить сервер с новым именем `--bvh-file`.

Формат калибровки JSON: `schema_version: 1`, `units: "m"`,
`extrinsics_convention: "world_to_camera"`, `cameras` — словарь по ID.
Каждая камера содержит `K` (3×3), `D` (коэффициенты OpenCV), `R` (3×3),
`t` (3, метры), `image_size: [width,height]`.
Соглашение: **Xcamera = R @ Xworld + t**. Мировые оси — X вправо,
Y вниз, Z вперёд относительно первой камеры. В WebGL/BVH используется
преобразование `(x, -y, -z)`, то есть Y вверх.

Текущий RTSP-ввод ставит метку **после декодирования на сервере**.
Он не извлекает время экспозиции из камер/RTP/RTCP. Группы кадров подбираются
по этому времени с допуском `--max-skew-ms 50`; кадры старше
`--max-age-ms 500` исключаются. Это ограничивает разницу времени доставки,
**но не доказывает синхронизацию экспозиций**. Для количественного сравнения
с IMU нужно измерить задержки и дрейф общим световым событием; затем
адаптировать приём аппаратных/источниковых временных меток под одноплатники.
Одинаковый FPS камер сам по себе недостаточен.

## Веб-интерфейс и API

В интерфейсе показаны камеры, ключевые точки, состояние соединений,
3D-скелет с вращением/масштабом, частота результатов и задержки.
Показатель «приём → результат» не включает неизвестную задержку до сервера.
Флажок «Ключевые точки» переключает обработанный кадр и исходное видео.
Точки нанесены на тот кадр, на котором выполнялся инференс.

| Адрес | Назначение |
|---|---|
| `/` | Веб-интерфейс |
| `/video/cam1.mjpg?overlay=true` | JPEG-поток обработанных кадров; `false` — исходное видео |
| `/api/state` | Текущее состояние, камеры, XYZ, BVH-кадр, диагностические данные |
| `/ws` | Те же JSON-состояния через WebSocket, максимум 20 сообщений/с |
| `/api/bvh/skeleton` | Описание BVH после определения длин костей; до этого HTTP 409 |
| `/api/calibration/board.png` | Изображение ChArUco-доски |
| `/api/calibration/capture`, `/solve`, `/reset` | POST: управление калибровкой |
| `/healthz` | Состояние процесса и модели |
| `/docs` | Описание HTTP API |

`pose.skeleton.points` содержит 17 XYZ в метрах в порядке `joint_names`.
Отсутствующие точки — `null`, а не нули или `NaN`. Перед реконструкцией
учитывается дисторсия. Отбрасываются точки с низким confidence, плохим
углом пересечения лучей, отрицательной глубиной или большой ошибкой репроекции.
С третьей камерой проверяются также гипотезы по парам видов.

Это режим **одного человека**. При нескольких детекциях в одном изображении
этот вид не участвует в восстановлении позы. Межкамерная идентификация людей
не реализована: в сцене должен быть один участник, даже если разные люди
попадают по одному в разные камеры.

## BVH по локальной сети

Получатель — наш хост; для него определён протокол **`visual-mocap-bvh/1`**.
Это передача BVH-иерархии и каналов в JSON, а не универсальный протокол,
который произвольная программа с импортом `.bvh` автоматически принимает.
Приёмник в существующем IMU GUI пока не подключён.

- `--bvh-target HOST:PORT` — адрес получателя. IPv6: `[ADDRESS]:PORT`.
- `--bvh-transport udp` — отдельный JSON в каждом UDP-пакете.
  Описание скелета повторяется каждые 2 секунды. Его размер может превышать
  MTU, поэтому в сетях, теряющих фрагментированные пакеты, предпочтителен TCP.
- `--bvh-transport tcp` — сервер захвата подключается к слушающему получателю.
  Каждый JSON заканчивается `\n`; первый пакет — описание скелета.
  После переподключения описание отправляется снова.
- `--bvh-units cm` — сантиметры, по умолчанию; `m` — метры.
  Углы в обоих случаях задаются в градусах, порядок **ZXY**.

Сообщение `type: "skeleton"` содержит `stream_id`, `skeleton_id`,
`hierarchy` (обычный текст BVH до секции `MOTION`), `joint_names`,
`channel_names`, `units`, `nominal_fps` и описание ограничений вращений.
В сообщении `type: "frame"` передаются:

```text
protocol, type, stream_id, skeleton_id, frame_id,
timestamp_monotonic_s, time_basis, source_frame_ids,
channels: [51 числовое значение], tracked: [16 булевых значений]
```

Первые три канала — положение Hips. Далее идут Zrotation, Xrotation,
Yrotation каждого сустава в порядке иерархии. `tracked` относится к суставам
из `joint_names`; это признак геометрической наблюдаемости, не численная
оценка точности. Направления кистей и стоп не измерены и отмечены `false`.
При потере корпуса приходит `type: "tracking_lost"` с причиной.

Получатель должен сопоставлять `(stream_id, skeleton_id)`, игнорировать
устаревшие/переставленные `frame_id`, ожидать описание неизвестного скелета
и считать поток потерянным при отсутствии новых кадров, например, 500 мс.
Для синхронизации с другим компьютером нельзя напрямую сравнивать
`timestamp_monotonic_s`: это часы **процесса отправителя/его машины**.
Протокол сохраняет реальные нерегулярные метки; `nominal_fps` — предел частоты.

Отправитель работает в отдельном потоке с одним последним ожидающим кадром.
Потери UDP, медленный TCP-получатель или отказ соединения не создают очередь
старых поз и не блокируют камеры. Отправка UDP не подтверждает доставку.

Минимальная проверка приёма UDP на целевом компьютере:

```python
import json
import socket

sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
sock.bind(("0.0.0.0", 7001))
while True:
    packet, sender = sock.recvfrom(65535)
    message = json.loads(packet)
    print(sender, message["type"], message.get("frame_id"))
```

### Вращения и файл BVH

После `--bvh-warmup 20` пригодных полных поз фиксируются медианные длины
сегментов. Затем положение таза и базисы корпуса вычисляются по XYZ,
конечности направляются вдоль измеренных костей. Продольный twist,
пронация/супинация, ориентации кистей и стоп этими 17 точками не определяются.
Для отсутствующей конечности удерживается предыдущее локальное вращение;
`tracked` показывает пропуск. При потере корпуса новый BVH-кадр не отправляется.
Модель не подгоняет длины костей в каждом кадре и не нормирует человека до 1,70 м.

`--bvh-file runtime/session_001.bvh` дополнительно сохраняет обычный BVH.
Запись идёт на диск с ограниченным потреблением памяти; файл `.part`
завершается и переименовывается при штатной остановке Ctrl+C.
Существующая запись не перезаписывается. В BVH используется равномерная
сетка `--fps` с удержанием последней позы, включая интервалы пропусков;
для измерения задержек нужен исходный сетевой поток с временными метками.
Аварийное завершение оставляет незавершённый `.part`.

## Проверки и границы готовности

Автоматические тесты:

```bash
.venv-visual-cpu/bin/python -m pip install pytest httpx
.venv-visual-cpu/bin/python -m pytest test_visual_mocap_server.py -q
```

Проверяются геометрия с дисторсией и выбросами, отсутствие ложного 3D,
калибровка по известным проекциям, отбор кадров, пустые/множественные
детекции, BVH-каналы и движение корня, равномерный BVH-файл, реальные
локальные UDP/TCP-сокеты, HTTP/WebSocket и запрет скрытого CPU fallback.

Дополнительно выполнены локальные проверки:

- настоящий YOLOX-m/RTMPose-m на изображении из RTMlib, ONNX Runtime CPU;
- два RTSP/H.264-потока через MediaMTX 1.21.3 и FFmpeg, обработка моделью,
  обрыв соединений, исчезновение устаревшей позы и автоматическое восстановление;
- Chrome: три живых изображения, WebGL, управление видом, переключение
  наложения точек, мобильная ширина; ошибок JavaScript не обнаружено.

Проверенное окружение: Python 3.12.14, NumPy 2.5.4,
OpenCV contrib headless 4.14.0.94, ONNX Runtime 1.31.1,
FastAPI 0.162.0, Uvicorn 0.54.0, websockets 16.1.1.
Версии клонов зафиксированы в
[`REPOSITORIES.json`](../../../equipment/VisualMoCap/REPOSITORIES.json).

Программа является прототипом сервера. Подключение ваших одноплатников,
измерения на целевом GPU, точность движений и синхронизацию с IMU нужно
проверить на физическом стенде. Обучение нейросети для этого не требуется.
