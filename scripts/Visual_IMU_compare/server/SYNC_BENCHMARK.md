# Бенчмарк синхронизации по светодиоду

Программа: [benchmark_sync.py](benchmark_sync.py). Работает в существующем
серверном окружении CPU или CUDA, без нейросетей, обучения и дополнительных
Python-пакетов. Отправитель `camera_streamer.py` менять не нужно: программа
подписывается на обычные потоки MediaMTX как ещё один RTSP-клиент.

## Что именно измеряется

Все камеры наблюдают **одно и то же неравномерное мигание**. Для каждого
декодированного кадра сохраняются номер, монотонная временная метка сервера,
прямоугольник светодиода (ROI) и средняя яркость. По одинаковым переходам
«выключен → включён» и «включён → выключен» оценивается относительное
рассогласование потоков, его разброс и изменение со временем.

**Это измерение по времени получения после декодирования, а не отдельное
измерение синхронности экспозиций.** В результат входят дискретизация и
экспозиция камер, кодирование, буферы, сеть и декодирование. Абсолютную
задержку от физического переключения LED до сервера без независимой метки
этого переключения определить нельзя. Время MCU с сервером не синхронизируется.

Одинаковый FPS не означает одинаковую фазу съёмки. При 30 FPS между кадрами
около 33,3 мс. Программа локализует переход между последним уверенно старым
и первым уверенно новым состоянием. Середина этого интервала используется
как оценка; дробные миллисекунды в JSON **не означают субмиллисекундную
точность**. Результат не является метрологической аттестацией стенда.
При rolling shutter разные строки кадра экспонируются в разное время:
наблюдение LED относится к его области, а не ко всему изображению сразу.

## Подготовка светового сигнала

1. Разместить LED/рассеиватель так, чтобы его видели все камеры. Если LED
   несколько, они должны управляться одним сигналом; независимые генераторы
   не подходят. Расположение камер и светодиода во время записи не менять.
2. Мигать с неравномерной длительностью каждого включения и выключения,
   например 200–850 мс при 30 FPS. Каждое состояние должно длиться несколько
   кадров. Одного импульса недостаточно для оценки разброса и дрейфа.
3. Желательна фиксация экспозиции, усиления и баланса белого, если камеры это
   позволяют. LED должен уверенно отличаться от фона. Он не должен занимать
   один пиксель или вызывать изменение яркости всей комнаты.
4. Выбрать ROI плотно вокруг светящегося элемента. Избыточный фон уменьшает
   контраст; другие мигающие объекты внутри ROI делают результат ненадёжным.
5. Записывать хотя бы 60–120 секунд; для медленного изменения задержки полезны
   несколько минут. Начать мигание до записи и продолжать до её завершения.

Равномерное периодическое мигание может совпасть после сдвига на целое число
периодов. Бенчмарк помечает такой сигнал `ambiguous_pattern` и не предлагает
поправку. Поиск внутри малого диапазона не превращает периодический LED
в однозначный временной код.

Пример генератора для Arduino-совместимого контроллера (загрузить отдельно,
к `camera_streamer.py` отношения не имеет):

```cpp
// Выберите подходящий вашей плате GPIO. Внешний LED подключается
// с токоограничивающим резистором; встроенный LED удобен для первого теста.
const int ledPin = LED_BUILTIN;
uint32_t rngState = 0x5A17B39Du;
uint32_t nextChange = 0;
bool on = false;

uint32_t nextRandom() {
  rngState ^= rngState << 13;
  rngState ^= rngState >> 17;
  rngState ^= rngState << 5;
  return rngState;
}
void setup() {
  pinMode(ledPin, OUTPUT);
  digitalWrite(ledPin, LOW);
  nextChange = millis() + 1000;
}
void loop() {
  uint32_t now = millis();
  if ((int32_t)(now - nextChange) >= 0) {
    on = !on;
    digitalWrite(ledPin, on ? HIGH : LOW);
    nextChange = now + 200 + nextRandom() % 651;
  }
}
```

Программа анализа не требует совпадения генератора с этим примером: она
сопоставляет наблюдаемые переходы. Регулярный PWM яркости вместо медленного
неравномерного включения/выключения для этого метода не подходит.

## Запуск на GPU-сервере или CPU-сервере

Сначала обычным способом запустить `rtsp_relay.py` и отправители камер.
В отдельном терминале из `scripts/Visual_IMU_compare/server/`:

```bash
.venv-cuda/bin/python benchmark_sync.py serve \
  --host 0.0.0.0 --port 8082 \
  --camera 'cam1=rtsp://127.0.0.1:8554/cam1' \
  --camera 'cam2=rtsp://127.0.0.1:8554/cam2' \
  --reference cam1 --duration 120 \
  --output runtime/sync
```

Для CPU заменить `.venv-cuda` на `.venv-cpu`. Для третьей камеры добавить
`--camera 'cam3=rtsp://127.0.0.1:8554/cam3'`. Поддерживаются 2–8 камер;
дублирующие URL отклоняются. Можно передать `--config cameras.json` с теми же
полями `id` и `source`, что у основного сервера; `offset_ms` при измерении
не применяется.

Открыть **http://IP_СЕРВЕРА:8082/**. TCP-порт 8082 должен быть доступен из LAN.
По умолчанию без `--host` сервер слушает только localhost. Интерфейс рассчитан
на доверенную локальную сеть и не имеет аутентификации.

1. На каждом изображении мышью/касанием выделить прямоугольник LED.
   В превью видны ROI, номер кадра, время приёма от запуска и яркость `I`.
2. Убедиться, что яркость явно меняется между включением и выключением.
   По умолчанию измеряется серая яркость; для цветного LED можно запустить
   программу с `--channel red`, `green` или `blue`.
3. Указать длительность и нажать **«Начать запись»**. Во время записи ROI
   заблокированы, чтобы не смешивать разные измерительные области.
4. Запись остановится по таймеру либо по кнопке **«Остановить и рассчитать»**.
5. Открыть отчёт. В нём таблица результатов и графики яркости/сдвига с выбором
   временного окна. HTML можно скопировать на другой компьютер и открыть
   без сервера и интернета.

ROI автоматически сохраняются в `runtime/sync/rois.json`. Повторный запуск:

```bash
.venv-cuda/bin/python benchmark_sync.py serve \
  --camera 'cam1=rtsp://127.0.0.1:8554/cam1' \
  --camera 'cam2=rtsp://127.0.0.1:8554/cam2' \
  --rois runtime/sync/rois.json \
  --duration 120 --autostart --exit-after-recording \
  --output runtime/sync
```

`--autostart` ждёт живых потоков и ROI для их текущего разрешения.
`--exit-after-recording` завершает процесс после сохранения отчёта.
Если потока нет или ROI не соответствует разрешению, автоматическая запись
не начинается; причину можно увидеть на странице/API. Ctrl+C завершает
текущую запись с анализом и закрывает RTSP-клиенты.

Не менять разрешение во время записи. Такой сеанс помечается недостоверным;
для нового разрешения нужно заново выделить ROI и начать новый сеанс.
При переподключении начинается новый сегмент; переход через разрыв не
считается вспышкой. Единый линейный тренд через переподключение не оценивается.

## Файлы и разметка

Каждая запись получает новый каталог `runtime/sync/ДАТА-ID/`:

| Файл | Содержимое |
|---|---|
| `session.json` | ROI, разрешения, опорная камера, параметры, версии, длительность и предупреждения |
| `cam1.csv`, `cam2.csv`, … | Каждое измерение: frame_id, segment, receive_monotonic_ns, t_s, brightness, размеры и ROI |
| `report.json` | События, интервалы переходов, статистика и сопоставления |
| `cam2-matches.csv`, … | Пары переходов относительно опорной камеры, номера кадров, сдвиг и его наблюдаемый интервал |
| `report.html` | Самодостаточный отчёт с таблицей и графиками |
| `cam1-segment1-roi.avi`, … | Необязательное видео области LED с номером кадра, временем и яркостью |

Чтобы сохранять размеченные видеоклипы области LED, добавить
`--save-roi-video`. По умолчанию сохраняются только численные измерения;
полное видео комнаты не записывается. Для AVI используется MJPEG, холст
320×160 и фиксированная частота воспроизведения 30 FPS. **Временная шкала —
CSV, а не время воспроизведения AVI**. Поле `roi_video_frame` связывает строку
CSV с индексом кадра клипа внутри данного сегмента; без видео оно равно −1.
Кодирование/запись видео добавляют нагрузку и могут влиять на измеряемую систему.

`frame_id` — локальный счётчик успешно декодированных кадров. Это не номер
кадра сенсора; пропуски исходных кадров по нему однозначно не обнаружить.
`segment` увеличивается после открытия нового RTSP-соединения.
`t_s` отсчитывается от начала сеанса; `receive_monotonic_ns` относится к часам
этого сервера после декодирования. PTS/RTP/время экспозиции не используются.

URL в метаданных очищаются от логина, пароля и query-параметров.
Все измерения находятся в `runtime/`, исключённом из Git.

## Как читать результат

Для каждого совпавшего перехода:

```text
Δ = время_перехода_камеры − время_перехода_опорной_камеры
```

Положительное Δ означает, что эта камера показала тот же переход позже
по времени приёма на сервере. Например, медиана +120 мс даёт пробную поправку
`offset_ms = -120` для основного сервера. Программа **не применяет её**.
Другие настройки/нагрузка, новый RTSP-сеанс и переменные сетевые задержки
могут изменить поправку. Большой сдвиг может также превышать глубину буфера
основного сервера (сейчас восемь кадров), поэтому число не стоит переносить
в конфигурацию без проверки.

| Поле отчёта | Значение |
|---|---|
| `offset_median_ms` | Медиана Δ за сеанс |
| `offset_p05_ms`, `offset_p95_ms` | 5-й и 95-й процентили Δ |
| `absolute_skew_p95_ms` | 95-й процентиль абсолютного рассогласования `abs(Δ)` |
| `jitter_p95_ms` | 95-й процентиль `abs(Δ − median(Δ))`, включая изменения со временем |
| `observed_trend_ms_per_min` | Линейное изменение относительной задержки; это не частота/дрейф аппаратных часов |
| `detrended_jitter_p95_ms` | Разброс после удаления оценённого линейного тренда |
| `transition_bracket_halfwidth_median_ms` | Медианная полуширина интервала разности двух переходов; не статистический CI |
| `trend_sampling_floor_ms_per_min` | Консервативный ориентир различимости тренда по длительности и дискретизации |
| `trend_above_sampling_floor` | Превышает ли модуль тренда этот ориентир; не тест статистической значимости |
| `matched_events`, `match_fraction` | Число пар и доля совпадений относительно меньшего числа событий |
| `suggested_offset_ms` | Минус медиана, только при однозначной и пригодной оценке |

Малый остаточный разброс после удаления большого постоянного сдвига не
означает, что исходные камеры были синхронны. Аналогично малый ненулевой
тренд ниже масштаба временной дискретизации нельзя трактовать как доказанный
дрейф. Для вычисления тренда нужны минимум 12 пар на интервале от 20 секунд
и один непрерывный сегмент с каждой стороны.

## Алгоритм и контроль пригодности

- Яркость — среднее в ROI по серому или выбранному цветовому каналу.
- Нижний/верхний уровни — 10-й/90-й процентили. Контраст меньше
  `--min-contrast 20` (шкала 0–255) отклоняется. Очень редкие короткие
  вспышки с низким заполнением для этих порогов не подходят.
- Два порога на 35%/65% диапазона и подтверждение двумя последовательными
  кадрами подавляют одиночные выбросы. Время события относится к первому
  кадру нового состояния, а не к кадру подтверждения.
- События одного знака сопоставляются один к одному в хронологическом порядке.
  Сдвиг ищется в пределах `--max-lag-ms 1000`, окно совпадения
  `--match-window-ms 80`. Это параметры поиска, не объявленная точность.
- Для пригодной оценки нужны минимум 12 пар, не менее 75% совпадений,
  отсутствие конкурирующего сдвига с близким качеством и отсутствие
  почти периодического сигнала. Проверяется также граница диапазона поиска.
- Через переподключение или паузу больше `max(200 мс, 4 × медианный интервал
  кадров)` событие не строится. Это диагностика времени доставки, а не
  точный счётчик потерянных сенсорных кадров.

| `status` | Что делать |
|---|---|
| `estimate_available` | Оценка пригодна в пределах описанного метода; проверить графики и интервалы |
| `insufficient_events`, `insufficient_matches` | Увеличить длительность; проверить ROI, видимость LED, пропуски |
| `ambiguous_pattern` | Использовать неравномерные длительности и более длинную уникальную последовательность |
| `lag_at_search_boundary`, `no_matches_in_search_range` | Проверить сигнал и при необходимости увеличить диапазон поиска |
| `capture_invalid` | Проверить предупреждения: смена разрешения, ошибка записи или незавершённый сеанс |

У отдельной камеры `low_contrast` означает отсутствие достаточной разницы
между включённым и выключенным состояниями. Красная строка отчёта означает,
что показанные кандидаты не следует использовать как надёжную поправку.

Пересчитать готовую запись с другими параметрами без камер:

```bash
.venv-cpu/bin/python benchmark_sync.py analyze runtime/sync/ДАТА-ID \
  --max-lag-ms 2000 --match-window-ms 80 --min-contrast 15
```

Исходные CSV сохраняются; отчёты этого сеанса пересчитываются.

## Контрольный прогон без камер

Быстрый воспроизводимый тест генерирует 120 секунд измерений без ожидания:

```bash
.venv-cpu/bin/python benchmark_sync.py demo --output runtime/sync-demo
```

У cam2 задано +120 мс; у cam3 −40 мс с линейным изменением +12 мс/мин.
Сэмплирование 30 FPS вносит заметную дискретизацию: от оценки не ожидается
точного равенства этим числам. Значение небольшого тренда может оставаться
ниже уровня различимости. Данные и отчёт явно помечены синтетическими.

Проверить веб-интерфейс на движущихся синтетических потоках:

```bash
.venv-cpu/bin/python benchmark_sync.py serve --demo --port 8082
```

ROI в этом режиме уже заданы. Автотесты:

```bash
.venv-cpu/bin/python -m pytest test_benchmark_sync.py -q
```

Проверяются знак и величина сдвига, дискретизация, известный линейный тренд,
пропущенные события, периодическая неоднозначность, слабый сигнал, разрывы,
поиск на границе диапазона, сохранение/повторный анализ и HTTP-цикл записи.
Реальная точность на нескольких физических камерах и общем LED должна быть
проверена на стенде. Наличие синтетических тестов такую проверку не заменяет.

Дополнительно выполнен полный локальный прогон через MediaMTX и два
синтетических RTSP/H.264-потока: по 751 записанному кадру, 48 пар переходов,
соответствие каждого кадра размеченного ROI-видео строке CSV, автоматическое
завершение и просмотр страницы/автономного отчёта в Chrome. Это проверка
тракта программы, а не измерение точности физических камер.

## Связь с основным сервером захвата

Бенчмарк можно запускать параллельно с `visual_mocap_server.py`, используя
другой HTTP-порт. Появляются дополнительные RTSP-подписки и декодеры;
нагрузка отличается от работы одного сервера. Полезно сравнить два сеанса:
только бенчмарк и бенчмарк вместе с захватом позы. Фиксировать режим камер,
нагрузку и наличие записи ROI-видео.

Метрики относятся к декодерам бенчмарка. Они не являются прямым измерением
того, какие пары кадров выбрал `select_frames()` основного сервера.
Для такого теста понадобится инструментирование именно его входного тракта.
Калибровка геометрии камер и инференс скелета здесь не нужны.

## Готовые решения и публикации

Проверено по первичным источникам 30.10.2026; эти проекты не устанавливаются
как зависимости нашего бенчмарка.

| Решение | Что уже реализовано | Отличие от этой задачи |
|---|---|---|
| [SkellySync / FreeMoCap](https://docs.freemocap.org/skellysync/) | Выравнивание записанных видео по аудио либо первому изменению яркости | Удобно для подготовки записей; готового измерителя изменяющейся задержки наших RTSP-входов это не даёт |
| [flashvideosynchronization](https://github.com/smidm/flashvideosynchronization) | Офлайн-синхронизация по вспышкам, оценка сдвига и дрейфа, учёт rolling shutter, графики и синхронизированные видео | Метод использует резкие изменения освещения значительной части кадра; заявленная субмиллисекундная точность требует его условий и не переносится на среднюю яркость маленького ROI |
| [RocSync, исходники](https://github.com/BAL-ROCS-BUT-COOL/RocSync) | LED-часы, схемы платы, прошивка и Python-декодер времени по кадрам | Более подходящее направление для точности порядка миллисекунд, но нужна специальная плата с оптическим временным кодом вместо одного обычного мигающего LED |

Для `flashvideosynchronization` авторы дают [страницу метода и публикацию](http://cmp.felk.cvut.cz/~smidm/rolling-shutter-camera-synchronization-with-sub-millisecond-accuracy.html).
SkellySync в FreeMoCap alpha.25 закреплён на ветке `philip/rewrite`; пакет
PyPI относится к более старой ветке, поэтому простая установка имени из
PyPI может дать другой API. Наш сервер пока использует из FreeMoCap только
DLT-триангуляцию и не подключает этот модуль синхронизации.

[Sensors, 2026, 26(3), 1036](https://www.mdpi.com/1424-8220/26/3/1036);
доступен также [авторский препринт](https://arxiv.org/abs/2511.14948).

в рамках этого бенчмарка он не проверялся.
