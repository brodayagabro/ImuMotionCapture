# Компьютер с камерой

[camera_streamer.py](camera_streamer.py) читает V4L2-камеру через FFmpeg
и публикует H.264 по RTSP/TCP на сервер. Необязательный `--preview`
включает страницу с живым изображением для настройки ракурса камеры.
Общая схема: [README эксперимента](../README.md).

## Установка

Из этого каталога:

```bash
./setup.sh --system-deps
source .venv/bin/activate
```

`--system-deps` устанавливает `python3-venv`, `ffmpeg`, `v4l-utils` через
apt/sudo. Если они уже есть, достаточно `./setup.sh`.
Python-пакеты находятся в **camera/.venv**. Системный Python и другие
окружения не изменяются. Нужен Python 3.10+; если системная версия старее,
setup получает приватный Python 3.12.

Для 64-битных x86/ARM доступен FFmpeg из закреплённого `imageio-ffmpeg`;
системный FFmpeg имеет приоритет. На других архитектурах нужен системный
FFmpeg. Проверяются поддержка V4L2 и кодировщик libx264.
Нейросети, MediaMTX и GPU-библиотеки здесь не устанавливаются.

Зависимости: [requirements.txt](requirements.txt),
[bootstrap](requirements-bootstrap.txt), [тесты](requirements-dev.txt).

```bash
./setup.sh --with-tests
.venv/bin/python -m pytest test_camera_streamer.py -q
```

## Запуск

Сначала на сервере должен работать [RTSP-ретранслятор](../server/README.md).

```bash
python camera_streamer.py --list-devices
python camera_streamer.py --device /dev/video0 --list-formats
python camera_streamer.py \
  --server 192.168.1.10 --port 8554 --name cam1 \
  --resolution 1280x720 --fps 30
```

Заменить IP адресом GPU-сервера. Для остальных камер использовать уникальные
имена `cam2`, `cam3`. Единственная камера определяется автоматически;
если их несколько, нужен `--device /dev/videoN` или стабильный путь
`/dev/v4l/by-id/...`. Узлы метаданных UVC не считаются видеокамерами.
На проверенном компьютере C920 находится на `/dev/video1`.

Обязательны **--server, --resolution, --fps**. Неподдерживаемая камерой
комбинация отклоняется. Изображение не масштабируется скрыто, кадры не
дублируются для искусственного FPS. Реальная частота может снижаться
из-за экспозиции, USB, нагрузки или сети.

| Параметр | Назначение |
|---|---|
| `--list-devices` | Найти подключённые камеры |
| `--device /dev/video1 --list-formats` | Показать разрешения, форматы и FPS выбранной камеры |
| `--resolution 1920x1080` | Разрешение; синоним `--size` |
| `--fps 30` | Частота; допустима дробь `30000/1001` |
| `--input-format auto` | Поддерживаемый формат, обычно MJPEG |
| `--encoder libx264` | CPU H.264, ultrafast/zerolatency, без B-кадров |
| `--bitrate 4M` | Целевой/максимальный битрейт |
| `--encoder h264_v4l2m2m` | Аппаратный кодировщик при наличии поддержки |
| `--encoder copy` | H.264 камеры без перекодирования |
| `--retry-delay 2` | Пауза перед переподключением |
| `--stall-timeout 15` | Перезапуск при отсутствии новых кадров |
| `--no-reconnect` | Завершение при ошибке |
| `--duration 10` | Ограничение времени теста |
| `--ffmpeg /path/to/ffmpeg` | Необязательное переопределение бинарника |
| `--preview` | Включить веб-превью на компьютере с камерой |
| `--preview-port 8081` | HTTP-порт превью |
| `--preview-host 0.0.0.0` | Адрес прослушивания; по умолчанию все IPv4-интерфейсы |
| `--preview-width 640` | Максимальная ширина превью, чётное число 32–1920 |
| `--preview-fps 10` | Частота превью 1–30, не выше частоты камеры |

Остановка — Ctrl+C/SIGTERM; камера освобождается. Недоступный получатель
и зависание процесса вызывают повторное подключение. Чужие процессы,
которые используют камеру, программа не останавливает.

## Доступные разрешения и FPS

Из каталога `camera/` узнать режимы **подключённой камеры** можно без
запуска трансляции и без GPU-сервера:

```bash
.venv/bin/python camera_streamer.py --list-devices
.venv/bin/python camera_streamer.py --device /dev/video1 --list-formats
```

Если камера единственная, достаточно `--list-formats` без `--device`.
Команда выводит форматы захвата, поддерживаемые разрешения и список FPS
для каждого разрешения. `--server`, `--resolution` и `--fps` для неё не нужны.

Ниже режимы **Logitech C920 на этом компьютере, `/dev/video1`**, прочитанные
через V4L2 30.10.2026. Для другой камеры или другого драйвера нужно повторить
команду: таблица не является универсальным списком для всех устройств.

| `--resolution` | FPS при `--input-format mjpeg` | FPS при `--input-format yuyv422` |
|---|---|---|
| 160x90 | 30, 24, 20, 15, 10, 7.5, 5 | 30, 24, 20, 15, 10, 7.5, 5 |
| 160x120 | 30, 24, 20, 15, 10, 7.5, 5 | 30, 24, 20, 15, 10, 7.5, 5 |
| 176x144 | 30, 24, 20, 15, 10, 7.5, 5 | 30, 24, 20, 15, 10, 7.5, 5 |

| 352x288 | 30, 24, 20, 15, 10, 7.5, 5 | 30, 24, 20, 15, 10, 7.5, 5 |
| 432x240 | 30, 24, 20, 15, 10, 7.5, 5 | 30, 24, 20, 15, 10, 7.5, 5 |

Это режимы, заявленные драйвером, а не результаты замеров устойчивого FPS
во всех сочетаниях. В частности, 720p и 1080p при 30 FPS требуют MJPEG;
при `--input-format auto` программа сама выбирает его для этих режимов.
`MJPG` в выводе V4L2 соответствует ключу `mjpeg`, `YUYV` — `yuyv422`.
Это форматы получения кадров с камеры; на сервер по-прежнему отправляется H.264.
H.264 как входной формат данный узел камеры не объявляет, поэтому
`--encoder copy` для него недоступен.

Например, явно выбрать 720p/30 FPS:

```bash
.venv/bin/python camera_streamer.py \
  --server 192.168.1.90 --device /dev/video1 \
  --resolution 1280x720 --fps 30 --input-format mjpeg --preview
```

Дробную частоту задавать с точкой: `--fps 7.5` (или `--fps 15/2`).

## Посмотреть ракурс через браузер

Добавить `--preview` к обычной команде отправки:

```bash
python camera_streamer.py \
  --server 192.168.1.90 --name cam1 --device /dev/video1 \
  --resolution 1280x720 --fps 30 \
  --preview
```

Открыть **http://IP_КОМПЬЮТЕРА_С_КАМЕРОЙ:8081/** с любого компьютера
локальной сети. Здесь нужен IP отправителя с камерой; `--server` по-прежнему
задаёт IP GPU-сервера. На самом компьютере с камерой можно открыть
`http://127.0.0.1:8081/`. Для другого порта добавить `--preview-port 8090`.
При активном firewall входящий TCP-порт превью должен быть доступен из LAN.
Это простой просмотр для доверенной локальной сети, без аутентификации.

Дополнительные Python-пакеты и повторный setup не нужны. Камера открывается
один раз: FFmpeg из того же входа формирует RTSP и JPEG-превью. По умолчанию
превью имеет ширину до 640 пикселей и частоту до 10 FPS, с сохранением
пропорций и без увеличения маленьких изображений. Параметры RTSP
`--resolution`/`--fps` остаются прежними. JPEG-кодирование добавляет нагрузку;
на слабом одноплатнике можно снизить её:

```bash
python camera_streamer.py --server 192.168.1.90 --name cam1 \
  --resolution 1280x720 --fps 30 \
  --preview --preview-width 320 --preview-fps 5
```

Несколько браузеров получают последний кадр; медленный клиент не создаёт
очередь кадров в захвате. Изображения хранятся только в памяти.
При остановке/зависании потока старый кадр скрывается, страница ожидает
восстановления. RTSP-ретранслятор нужен и для режима с превью: при потере
соединения FFmpeg перезапускается вместе с обеими ветвями видео.
HTTP-страница остаётся доступной во время повторных подключений.
Ctrl+C/SIGTERM завершает и отправку, и HTTP-сервер.

Без `--preview` HTTP-порт не открывается и JPEG-превью не кодируется.

## Повторный запуск каждые 15 секунд: проверка RTSP

Сообщение `No new frames` (в новых версиях `No encoded-output progress`)
означает, что FFmpeg не сообщил о новых выходных кадрах. Причиной может
быть недоступный RTSP-сервер, даже если камера исправно снимает.
Предупреждения `deprecated pixel format` и `-vsync is deprecated` сами
по себе не объясняют зависание: они встречаются и при успешном захвате.

С **проблемного компьютера с камерой** проверить TCP-подключение:

```bash
python3 -c 'import socket; s=socket.create_connection(("192.168.1.90", 8554), timeout=3); print("RTSP TCP reachable:", s.getpeername()); s.close()'
```

`TimeoutError` указывает на фильтрацию/проблему маршрута; `Connection refused`
обычно означает, что на этом адресе/порту никто не слушает, либо соединение
явно отклоняется. Успешное TCP-подключение ещё не доказывает, что разрешена
RTSP-публикация. Проверить также сообщения `rtsp_relay.py` и уникальность
имён `cam1`, `cam2`, `cam3`.

Если на сервере включён UFW, для нашей подсети команды выполняются
**на GPU-сервере 192.168.1.90**:

```bash
sudo ufw status numbered
sudo ufw allow from 192.168.1.0/24 to any port 8554 proto tcp
```

При другой LAN-подсети заменить `192.168.1.0/24`. Доступность веб-страницы
на 8080 не означает доступности RTSP на 8554. Правило только для одного
адреса камеры не разрешит подключение остальным компьютерам. Если в UFW
есть более ранние явно запрещающие правила, нужно проверить их порядок.
После изменения правила повторить TCP-проверку и обычный запуск отправителя.

Проверенный пример 31.10.2026: встроенная камера Dell успешно выдала 90 кадров
640×480 при примерно 30 FPS, но TCP 8554 с `192.168.1.61` не подключался,
хотя SSH и HTTP сервера были доступны. С другого компьютера той же LAN
RTSP отвечал. Увеличение `--stall-timeout` такую сетевую проблему не устраняет.

## Ограничения и проверка

Поддерживаются дискретные режимы Linux V4L2. Для libcamera-only CSI-камер,
нестандартных форматов и stepwise/continuous-режимов нужен адаптер.
При ошибке доступа проверить права на устройство и группу `video`.

На Logitech C920 проверены 1280×720/30 FPS и 640×480/15 FPS, приём сервером
захвата и восстановление после перезапуска MediaMTX. Использовались loopback,
FFmpeg 7.0.2 и MediaMTX 1.21.3; видео в файл не записывалось.
Аппаратное кодирование на одноплатниках нужно проверить отдельно.

Веб-превью проверено на C920 одновременно с RTSP 1280×720/30 FPS:
JPEG 640×360, два клиента, отображение в Chrome, обрыв и восстановление
RTSP, освобождение камеры и HTTP-порта после SIGTERM. Автотесты проверяют
сборку JPEG из частей, отсутствие устаревших изображений, HTTP и чтение
FFmpeg-выхода без подключённых зрителей.

У разных камер одинаковый FPS не означает синхронную экспозицию.
[Ограничения серверного захвата](../server/README.md).

[FFmpeg V4L2](https://ffmpeg.org/ffmpeg-devices.html#video4linux2_002c-v4l2),
[RTSP-публикация MediaMTX](https://mediamtx.org/docs/publish/ffmpeg).
