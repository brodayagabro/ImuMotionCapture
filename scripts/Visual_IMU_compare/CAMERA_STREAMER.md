# Передача видео с Ubuntu/Debian на сервер

[`camera_streamer.py`](camera_streamer.py) читает Linux V4L2-камеру через FFmpeg
и публикует H.264 по **RTSP/TCP** на указанный сервер. Веб-интерфейса нет.
Python-программа управляет камерой, параметрами и переподключением;
видеоданные идут через FFmpeg без копирования кадров в Python.

Схема:

```text
USB/V4L2-камера → camera_streamer.py / FFmpeg
               → RTSP на GPU-сервере / MediaMTX
               → visual_mocap_server.py → RTMPose → WebGL/BVH
```

`visual_mocap_server.py` читает RTSP как клиент. Для режима, в котором
одноплатник сам отправляет видео на IP сервера, нужен RTSP-ретранслятор.
Он запускается на GPU-сервере, один на все камеры, через `--relay` этого
же Python-файла. Камерам не требуется входящее сетевое подключение.

## 1. На сервере: запустить RTSP-приём

Установить MediaMTX из [официальных релизов](https://github.com/bluenviron/mediamtx/releases)
для архитектуры сервера, распаковать и указать путь к исполняемому файлу:

```bash
python3 camera_streamer.py --relay --mediamtx /path/to/mediamtx --port 8554
```

По умолчанию ретранслятор слушает `0.0.0.0:8554`. Можно задать `--bind`.
Он не запускает HTTP/WebRTC/HLS-сервисы. Конфигурация и служебные файлы
создаются во временном каталоге. Остановка — Ctrl+C или SIGTERM.
Повторная публикация другим компьютером под уже занятым именем отклоняется.

Для проверки на текущем компьютере MediaMTX уже скачан в ходе тестирования:

```bash
python3 camera_streamer.py --relay \
  --mediamtx runtime/rtsp-smoke/mediamtx --bind 127.0.0.1
```

Этот путь — локальный тестовый артефакт; бинарный файл в Git не включён.
Протокол и конфигурация проверены с MediaMTX 1.21.3.
Для внешнего компьютера нужен доступ к TCP-порту 8554.
Конфигурация предназначена для доверенной локальной сети, без аутентификации.

## 2. На компьютере с камерой

Достаточно Python 3.9+ и системных утилит; conda, OpenCV и Python-пакеты не нужны:

```bash
sudo apt update
sudo apt install python3 ffmpeg v4l-utils
```

Найти камеру и посмотреть её режимы:

```bash
python3 camera_streamer.py --list-devices
python3 camera_streamer.py --device /dev/video0 --list-formats
```

Запустить передачу, заменив IP адресом GPU-сервера:

```bash
python3 camera_streamer.py \
  --server 192.168.1.10 --port 8554 --name cam1 \
  --device /dev/video0 --resolution 1280x720 --fps 30
```

Для второй камеры на другом компьютере использовать `--name cam2`,
для третьей — `--name cam3`. **Имена должны быть уникальными.**
На текущем компьютере C920 доступна через **`/dev/video1`**, а не `/dev/video0`.
Если доступна ровно одна камера, `--device` можно не указывать.
Метаданные UVC, например `/dev/video2` у C920, не считаются видеокамерой.
Для постоянной установки предпочтителен стабильный путь `/dev/v4l/by-id/...`.

Обязательные параметры трансляции: **`--server`, `--resolution`, `--fps`**.
Программа проверяет заявленные камерой разрешение, формат и FPS и отказывается
от неподдерживаемой комбинации. Она не масштабирует неподходящий режим
и не дублирует кадры, чтобы искусственно получить нужный FPS.
Реальная частота всё равно может снизиться из-за экспозиции, USB,
производительности кодирования или сети; в консоли выводится частота кодирования.

## 3. Подключить потоки к захвату движений

На том же сервере, где запущен MediaMTX:

```bash
.venv-visual-cuda/bin/python visual_mocap_server.py \
  --device cuda:0 --host 0.0.0.0 \
  --camera 'cam1=rtsp://127.0.0.1:8554/cam1' \
  --camera 'cam2=rtsp://127.0.0.1:8554/cam2' \
  --camera 'cam3=rtsp://127.0.0.1:8554/cam3' \
  --calibration runtime/calibration.json \
  --bvh-target 192.168.1.20:7001
```

Для локальной CPU-проверки заменить окружение на `.venv-visual-cpu`
и устройство на `--device cpu`. Указывать только реально запущенные камеры.
Видео можно проверить также в VLC по `rtsp://IP_СЕРВЕРА:8554/cam1`.
Калибровка и BVH описаны в [SERVER.md](SERVER.md).

## Параметры кодирования и устойчивость

| Параметр | Значение |
|---|---|
| `--resolution 1920x1080` | Запрашиваемое разрешение камеры; также доступен `--size` |
| `--fps 30` | FPS; допустима дробь `30000/1001` |
| `--input-format auto` | Выбирает поддерживаемый формат; обычно MJPEG для USB-камер |
| `--input-format mjpeg` | Явно запросить MJPEG от камеры |
| `--encoder libx264` | CPU H.264, по умолчанию, ultrafast/zerolatency, без B-кадров |
| `--bitrate 4M` | Целевой/максимальный битрейт кодирования |
| `--encoder h264_v4l2m2m` | Аппаратный кодировщик V4L2 M2M, если доступен на одноплатнике |
| `--encoder copy` | Передавать H.264 камеры без перекодирования; камера должна его выдавать |
| `--retry-delay 2` | Пауза перед повторным открытием камеры/соединения |
| `--stall-timeout 15` | Перезапуск, если счётчик кадров не увеличивается 15 секунд |
| `--no-reconnect` | Завершиться при ошибке вместо повторных попыток |
| `--duration 10` | Ограничить тест 10 секундами, включая попытки подключения |
| `--ffmpeg /path/to/ffmpeg` | Явный путь к FFmpeg |

Сжатие выполняется на компьютере с камерой. Кодирование 1080p может быть
слишком тяжёлым для слабого одноплатника: нужно измерить загрузку и частоту,
затем выбрать аппаратный кодировщик или меньшие разрешение/FPS.
V4L2 M2M и H.264 passthrough добавлены как варианты, но на C920 данного
компьютера они не проверены: камера здесь предоставляет MJPEG и YUYV.

Поддерживается перечисление дискретных режимов V4L2. Камеры с libcamera-only
CSI-интерфейсом, нестандартными пиксельными форматами или только stepwise/continuous
режимами потребуют отдельного адаптера. На неподдерживаемом устройстве программа
завершится с диагностикой, вместо неподтверждённого выбора параметров.

Если доступ запрещён, проверить права на `/dev/video*` и членство пользователя
в группе `video`. Если устройство занято, завершить другое приложение,
использующее эту камеру. Программа не останавливает чужие процессы.

Новый отправитель **не обеспечивает аппаратную синхронизацию камер**.
Действующие ограничения временных меток серверного RTSP-ввода сохраняются:
перед количественным сравнением с IMU нужно проверить время съёмки и задержки.

## Проверки

```bash
.venv-visual-cpu/bin/python -m pytest test_camera_streamer.py -q
```

Тесты проверяют выбор точного режима, дробный FPS, команды кодирования,
отсутствие искусственного CFR, параметры адреса/порта, обработку stdout/stderr,
остановку по таймеру и обнаружение зависшего потока.

На подключённой Logitech C920 (`/dev/video1`) выполнена аппаратная проверка:

- 1280×720, MJPEG → H.264/RTSP, заявленные 30 FPS; кодировщик сообщал около 30 FPS;
- 640×480, MJPEG → H.264/RTSP, заявленные 15 FPS; приём около 15 FPS;
- реальный поток принят существующим `visual_mocap_server.py` с CPU-инференсом;
- отправитель восстановил передачу после остановки и повторного запуска MediaMTX;
- после остановки все тестовые процессы завершены, камера освобождена,
  исходный режим 640×480 MJPEG / 30 FPS восстановлен. Видео в файл не записывалось.

Тест выполнен через локальную сеть loopback этого компьютера, с FFmpeg 7.0.2
и MediaMTX 1.21.3. Скорость извлечения первых кадров из буфера не является
измерением FPS камеры; пропускную способность и задержку физической LAN
нужно проверить при установке на отдельные компьютеры.

Документация используемых компонентов:
[V4L2 в FFmpeg](https://ffmpeg.org/ffmpeg-devices.html#video4linux2_002c-v4l2),
[RTSP-публикация FFmpeg в MediaMTX](https://mediamtx.org/docs/publish/ffmpeg).
