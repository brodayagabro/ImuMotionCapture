# Синхронный эксперимент IMU + Noitom

Отдельное приложение поверх `pyqt_mocap`: ESP32/MPU6050 и Noitom в одном
OpenGL-окне, общий `time.monotonic_ns()`, независимые исходные потоки и одна
кнопка REC. Собственная система — синий заполненный скелет, Noitom — красный
каркас. Общие размеры тела и неподвижный таз позволяют сравнивать направления
пяти сегментов. Оценка точности, DTW/RMSE и распознавание слов не выполняются.

## Запуск

Из корня репозитория, Python 3.11+ и существующее окружение проекта:

```powershell
.venv\Scripts\python.exe scripts\noitom_comparison\main.py
```

Если окружение ещё не установлено:

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -e ".[dev]"
```

Без костюма и SDK можно проверить красную анимированную модель:

```powershell
.venv\Scripts\python.exe scripts\noitom_comparison\main.py --fake
```

В блоке Noitom нажмите **Connect**, затем **Start**. Режим явно отмечен
`SYNTHETIC`, включая metadata. Синяя модель остаётся в исходной позе до
подключения ESP32. Fake-клиент не подменяет поток ESP32 и его калибровку.

Также поддерживается `python -m scripts.noitom_comparison.main` из корня.
Приложение использует те же сохранённые настройки ESP32, что обычный viewer.
В экспериментальном окне кнопка **«Калибровка»** сразу запускает короткий мастер
**A → T → A** для собственной системы. `pyqt-mocap` и `pyqt-mocap-gl` сохраняют
прежние мастера калибровки и не импортируют SDK.

## Внешние события

При запуске через `main.py` доступен универсальный TCP-приёмник меток:
`127.0.0.1:5055`. Порт задаётся `--event-port`, значение `0` отключает сервер.
Он слушает только loopback и не влияет на порты потоков костюмов. Ошибка
занятого порта отображается в окне, захват MoCap остаётся доступным.
При программном создании `ComparisonConfig` сервер по умолчанию выключен.

Это общий интерфейс: в рекордере нет слов, жестов или таймингов конкретного
эксперимента. Пример отдельного отправителя —
[семафорный демонстратор](../experiments/semaphore/README.md).

Протокол: UTF-8 JSON, один объект и `\n` на сообщение, не более 64 КиБ.
После открытия соединения клиент отправляет:

```json
{"type":"hello","protocol_version":1}
```

Ответ, если включена запись REC:

```json
{"type":"ready","protocol_version":1,"ready":true,"recording_session_id":"<id записи>"}
```

Без REC возвращаются `ready=false` и `recording_session_id=null`.
`{"type":"ping"}` возвращает такое же актуальное состояние. Готовность означает
наличие активной записи, а не проверку качества или наличия потоков костюмов.

Произвольное событие (имена `hello` и `ping` зарезервированы):

```json
{"type":"stimulus_start","event_id":"<уникальный id>","recording_session_id":"<id записи>","experiment":"example","trial_id":1}
```

Сервер добавляет `time.monotonic_ns()` при получении полного сообщения,
проверяет активную сессию и атомарно ставит событие в очередь записи. Все
дополнительные поля сохраняются без интерпретации в `details_json` файла
`events.csv`. Основные колонки — `host_timestamp_ns`, `relative_timestamp_ns`,
`event`, `details_json`. Время отправителя не подменяет время рекордера.

После принятия каждого события возвращается:

```json
{"type":"ack","event_id":"<уникальный id>","accepted":true,"host_timestamp_ns":123456789,"recording_session_id":"<id записи>"}
```

ACK подтверждает очередь, а не `fsync`. При остановленной записи или смене ID
возвращается `accepted=false` с `reason=recording_inactive` либо
`recording_session_changed`. Некорректный JSON/handshake/размер даёт ответ
`type=error` и закрывает только это соединение. Сервер не повторяет события
и не выполняет дедупликацию: клиент должен использовать уникальные `event_id`
и не переотправлять старые метки с новой временной меткой.

Начиная с добавления реестра датасета успешный ACK также содержит
`recording_path` — абсолютный путь каталога записи. Это позволяет отправителю
сохранить точную связь даже при нестандартном `--recordings-dir`. Новое поле
не меняет временные метки и не добавляет в рекордер логику эксперимента.

## Mocap API и Axis Studio

Используется официальный [Mocap API Noitom](https://github.com/pnmocap/MocapApi),
его C procedure tables с версиями и порядком вызовов из рабочего `demo/demo-py`.

SDK хранится отдельным локальным checkout и исключён из Git проекта. Версия,
использованная при проверке: `a62cb6dfc33fc74631c5732bd90f7a91bebe622a`.
Все текущие изменения отслеживаемых файлов SDK сохранены в
`patches/mocap-api-local.patch`: исправления Python demo/обёртки и изменённые
метаданные Python-пакета. Сгенерированные `build` и `__pycache__` не сохраняются.
Чтобы восстановить SDK в новой копии проекта, выполните из корня:

```powershell
git clone https://github.com/pnmocap/MocapApi.git scripts/MocapApi
git -C scripts/MocapApi checkout --detach a62cb6dfc33fc74631c5732bd90f7a91bebe622a
git -C scripts/MocapApi apply ../noitom_comparison/patches/mocap-api-local.patch
```

В существующем checkout эти правки уже применены; повторно применять патч не нужно.
Отдельная установка Python wrapper не требуется. Локальная копия SDK уже
находится в `scripts/MocapApi`; заголовки и
бинарные файлы SDK экспериментальное приложение не меняет.

Пути по умолчанию:

| Платформа Python | Библиотека |
| --- | --- |
| Windows x64 | `scripts/MocapApi/demo/demo-py/MocapApi/mocap_api/lib/amd64/MocapApi.dll` |
| Linux x64 | `scripts/MocapApi/demo/demo-py/MocapApi/mocap_api/lib/x86_64/libMocapApi.so` |
| Linux ARM64 | `scripts/MocapApi/demo/demo-py/MocapApi/mocap_api/lib/arm64/libMocapApi.so` |

В первую очередь выбирается библиотека из `demo-py`; если её нет, используется
старый путь `bin/win32/x64/release` или `bin/linux/{x64,aarch64}`. В этом
репозитории Windows DLL из demo имеет версию `0.0.73.19a54f85`, а DLL из `bin` —
`0.0.17.a6e15748`. Живой поток проверен с версией из demo. Версия, полный путь
библиотеки, порт и режим приёма выводятся в мониторе и сохраняются в metadata.

Разрядность Python и библиотеки должна совпадать. Оставьте зависимости SDK рядом
с библиотекой либо в системном пути загрузчика. Любой другой путь можно передать
явно; отсутствие DLL выдаёт ошибку только в блоке Noitom:

```powershell
.venv\Scripts\python.exe scripts\noitom_comparison\main.py --sdk-library "D:\MocapApi\MocapApi.dll" --port 7012
```

1. В Axis Studio подключите костюм и выполните его штатную калибровку.
2. Включите **BVH broadcasting**, направление — IP компьютера с приложением,
   UDP-порт **7012**, как в `demo-py` (или значение `--port`). Для разных компьютеров используйте
   LAN IP, а не `127.0.0.1`. Разрешите этот UDP-порт в межсетевом экране.
3. Выберите **Binary BVH**, включённые displacement/transformation и порядок
   вращений **XYZ**, как в `demo-py`. Другой порядок задаётся `--bvh-rotation ZXY`
   (поддерживаются все шесть порядков). Если Axis Studio настроен на другой формат, согласуйте его
   через `--bvh-format string` или `--bvh-format legacy` (старый бинарный header).
   Для этой итерации требуется поток BVH с иерархией и локальными вращениями.
4. В приложении **Noitom Connect** создаёт и настраивает SDK application;
   **Start** открывает приём, **Stop** закрывает приём, **Disconnect** освобождает
   SDK. Эти кнопки не запускают и не останавливают захват костюма в Axis Studio.
5. Для TCP: `--transport tcp --server 192.168.1.10 --port 7012`, где IP и порт
   соответствуют серверу вещания Axis Studio.

Если передаётся несколько актёров, используйте `--avatar-index N`. Без него
выбирается первый полученный актёр до следующего Disconnect. Индекс и имя актёра
сохраняются в каждом кадре; актёры не смешиваются.

Приём повторяет `demo-py`: сначала `PollApplicationNextEvent(NULL, &count, app)`,
затем заполнение массива событий с заданным `size` каждого элемента. Одного
вызова с заранее выделенным массивом недостаточно: на живом потоке он возвращал
ноль событий. Вызовы SDK и копирование всех суставов выполняются в одном worker.
Режим записывается как `noitom.delivery_mode = "poll_latest"`. SDK может
объединять обновления **до передачи приложению**.
Пропуски, повторы и сбросы доступного SDK frame index записываются
как `noitom_frame_index_discontinuity`, сессия становится `incomplete`.
Приложение не может восстановить кадры, которых SDK не предоставил.

## Порядок эксперимента

1. Подключиться к ESP32 существующей кнопкой, нажать **START**.
2. Нажать **«Калибровка»** и выполнить **A → T → A**: руки вниз, прямые руки
   горизонтально в стороны, снова руки вниз. На каждом этапе — 5 секунд
   подготовки и 5 секунд записи, всего около 30 секунд. Допуск колебаний
   ориентации при удержании позы — **15°**. Либо импортировать сохранённый профиль.
   При расчёте используется физическая продольная ось датчика: **+Y к кисти
   слева, −Y к кисти справа** (для плеча и предплечья). Её направления в A- и
   T-позах задают согласование осей каждой руки. Это устраняет произвольный
   поворот плоскости сгибания локтя, который оставался при согласовании только
   оси подъёма. Прокручивание датчика вокруг локальной Y не заменяет подъём руки.
   Настройки перестановок осей сохраняются; прежняя непрерывная поправка рук
   вычисляется заново. Для корпуса и выключенных датчиков сохраняется прежняя поправка.
   Конечная A-поза проверяет возврат и задаёт новую нейтраль. Оценка изменения
   ориентации сохраняется для диагностики, автоматическое вычитание дрейфа отключено.
   При расхождении возврата более 30° профиль не применяется: мастер сохраняет
   этапы и предлагает «Повторить последнюю A-позу» или «Начать заново».
   Для рук проверяется направление физической продольной Y непосредственно
   по входным кватернионам. Вращение только вокруг этой оси не считается
   ошибкой возврата. Причину расхождения нельзя определить по одному углу.
   При активной REC в `events.csv` сохраняются события `own_calibration_pose_captured`
   и `own_calibration_fit_rejected`: точные интервалы, средние/краевые кватернионы,
   разброс, количество кадров, соответствие датчиков и ошибки всех сегментов.
   Неудачная попытка сохраняется даже без применённого профиля.
   Отклонение возврата более 30° отклоняет результат, более 15° даёт рекомендацию
   повторить калибровку. В профиль и метаданные записи попадают метод
   `a_t_a_sensor_y` и только три фактически записанные позы. При переходе со
   старого метода `a_t_a` нужно заново выполнить калибровку. Датчики должны быть
   закреплены осью Y вдоль соответствующих сегментов, корпус в A/T остаётся
   неподвижным. Точность движений в других плоскостях процедура отдельно не измеряет.
3. Подключить и запустить Noitom. В обеих системах человек должен смотреть в
   согласованном направлении. Проверить A-позу, T-позу, подъём каждой руки и
   движение вперёд; автоматическое выравнивание heading не выполняется.
4. Проверить включённые датчики: по умолчанию основной viewer исключает `spine`.
   Чтобы сравнивать измеренный корпус, включите его в существующих настройках.
   Для Noitom откройте **Настройки → Noitom**: отдельно выбираются корпус (спина),
   левое/правое плечо и предплечье. Спина Noitom по умолчанию выключена;
   выбор сохраняется между запусками. Снятая галочка исключает ориентацию
   сегмента из отображаемой и записываемой позы: он получает исходную ориентацию
   и бледный цвет, остальные выбранные сегменты продолжают обновляться.
   Можно отключить все сегменты. Настройки применяются без перезапуска приёма.
   Полная исходная иерархия SDK сохраняется для последующего анализа, включая
   родительские суставы, необходимые для вычисления ориентаций рук.
5. Нажать **REC · эксперимент**, выполнить движение, нажать **STOP REC**.
6. Дождаться окончания сохранения. Следующий REC создаёт новую папку.

Старая запись/экспорт BVH собственной системы остаётся независимой. BVH Noitom
в этой итерации не экспортируется. Не используйте равномерный BVH вместо raw
потоков для анализа задержек.

При остановке, отключении, ошибке источника или STALE запись продолжается для
другого источника, но сессия помечается `incomplete`. Отсутствующие потоки тоже
помечаются. Ошибка диска отображается в строке сессии и завершает запись.
STALE по умолчанию наступает через 500 мс (`--stale-timeout-ms`). Последняя поза
при STALE остаётся на экране; её возраст виден в статусе. При Disconnect/Error
красная модель скрывается. Закрытие окна дожидается обработки очереди и записи.

## Оси и ориентации

SDK получает встроенный preset **Default**, как в `demo-py`: правая система,
Y вверх, сантиметры. Параметры проверяются чтением из SDK. Произвольные render
settings в проверенной DLL приводили к `Error_NotSupported` при чтении вращений.
Целевая система проекта: **+X — вправо, +Y — вперёд, +Z — вверх**. Смена базиса
выполняется в Python: `position = 0.01 * (-sdk_x, sdk_z, sdk_y)`;
SDK `xyzw` становится нормализованным `wxyz = (w, -x, z, y)`.
Это соответствует `R_project = B @ R_sdk @ B.T`, где
`B = [[-1,0,0], [0,0,1], [0,1,0]]`. Исходные значения SDK также сохраняются.

`noitom_adapter.py` собирает мировое вращение по родительской цепочке, затем
применяет коррекцию направления кости, найденную по SDK default child offset.
Если SDK его не предоставляет (живой BVH возвращает `Error_NotSupported`),
используется локальное смещение дочернего сустава из текущего BVH-кадра.
Мировое направление кости равно `R_parent_world @ child_local_position`.
Коррекция переводит исходное направление A-позы манекена в соответствующее
направление соответствующей кости Noitom. Поэтому локальные SDK rotations
нельзя напрямую передавать в `compute_body_pose`. Коррекция направления не
является оценкой или отдельной калибровкой ESP32; анатомический twist по одним
направлениям костей не определяется, и этот режим предназначен для сравнения
направлений сегментов. Для физического согласования осей нужна проверка на
реальном костюме.

После калибровки своей системы включите оба потока, встаньте прямо лицом
в исходном направлении калибровки и нажмите **«Совместить направление»**.
Эта кнопка устраняет различие начального курса: одного преобразования Y-up/Z-up
и общего таза недостаточно, поскольку SDK и IMU могут иметь разные нули поворота.
Направление Noitom определяется по линии плеч из полной иерархии, даже если
захват спины выключен. Применяется один фиксированный поворот вокруг вертикали;
он сохраняет углы суставов и последующие повороты корпуса. Ошибки калибровки
отдельных IMU этой кнопкой не исправляются. При новом подключении Noitom
поворот сбрасывается; после новой калибровки IMU совмещение следует повторить.

| SDK joint/tag | Сегмент проекта |
| --- | --- |
| Spine2 / 9 | spine |
| LeftArm / 37 | shoulder.L |
| LeftForeArm / 38 | forearm.L |
| RightArm / 14 | shoulder.R |
| RightForeArm / 15 | forearm.R |

LeftShoulder/RightShoulder — ключицы, поэтому они не используются как плечевые
сегменты. Полная предоставленная SDK иерархия сохраняется. Root translation
сохраняется, но не участвует в отображении. Ошибка иерархии или отсутствие и
default, и текущего локального смещения не заменяются выдуманными ориентациями: raw кадр сохраняется с
`mapping_error`, красная модель не обновляется, сессия помечается `incomplete`.

## Файлы сессии

По умолчанию `<repository>/recordings/<local-date-time>_<unique-id>/`:

| Файл | Содержимое |
| --- | --- |
| `metadata.json` | Версия схемы, T0/STOP, clock, конфигурация, профиль и состояние калибровки, SDK version/delivery mode, оси, mapping, счётчики и итоговый статус |
| `own_packets.jsonl` | Каждый UDP datagram: неизменный payload в base64, адрес, wall time, host/relative ns, результат разбора |
| `own_frames.jsonl` | Каждый опубликованный моделью кадр: frame header/index, исходные нормализованные sensor quaternions текущего пакета с каноническими ID и откалиброванные/сглаженные segment orientations |
| `noitom_frames.jsonl` | Каждое предоставленное SDK обновление выбранного актёра: SDK timestamp/index, полная локальная иерархия с position/rotation/default position/tag в базисе проекта, исходные sdk_position/sdk_rotation_xyzw/sdk_default_position и segment orientations |
| `events.csv` | Начало/конец, команды, изменения калибровки, остановки, stale/resume, ошибки и разрывы SDK индексов |

Каждая строка raw потока содержит целочисленные `host_timestamp_ns` и
`relative_timestamp_ns = host_timestamp_ns - recording_t0_ns`. JSONL выбран,
чтобы не терять иерархию SDK, исходный datagram и необязательные поля.
`raw_sensor_quaternions` отражает только датчики, обновлённые текущим пакетом;
`segment_orientations` — состояние модели после него, включая удержанные значения.
`enabled_segments` и `neutral_pending` позволяют отличить измеренную/калиброванную
позу от исходных или выключенных сегментов. Точные исходные числа доступны в
payload, нормализация sensor quaternion выполнена существующим парсером.

В Noitom-кадрах `enabled_segments` фиксирует выбор для данного кадра,
`segment_orientations` содержит только выбранные сегменты. Начальный выбор
записан в `metadata.noitom.enabled_segments`, изменения во время записи —
в событиях `noitom_enabled_segments_changed`. Replay учитывает выбор каждого
кадра, включая полностью отключённую позу; старые записи без этого поля
воспроизводятся со всеми сегментами.

`heading_offset_rad` в каждой строке Noitom указывает применённый поворот
вокруг вертикали. `segment_orientations` уже учитывает его, поэтому replay
воспроизводит показанную позу без повторного поворота. Исходная иерархия `joints`
сохраняется до совмещения. Начальное значение записано в metadata, нажатия
кнопки — в событиях `noitom_heading_aligned` вместе с меткой опорного кадра.

Метка ставится сразу после ESP32 `recvfrom` или после возврата SDK poll, до
чтения суставов. Это **время получения данных приложением на host**, а не время
физического измерения и не аппаратная синхронизация. SDK timestamp хранится как
отдельное значение без предположений о его эпохе. Float seconds используются
только на границе существующих model/BVH API; исходные ns сохраняются целиком.

Ни кадры, ни строки двух файлов не сопоставляются по индексам. Частоты могут
отличаться, интерполяции/ресемплинга нет. При STOP приём новых записываемых кадров
прекращается атомарно; уже принятые кадры остаются закреплены за своей сессией и
дописываются после обработки очереди. Диск обслуживает отдельный worker.
GUI/renderer не отбрасывает кадры записи, однако пропуски транспорта и самого
SDK возможны. Очереди не имеют искусственного лимита с молчаливым отбрасыванием:
для длительной записи нужны достаточные память и скорость диска.

**latest-frame Δ не является измерением аппаратной задержки двух систем.**
Это только разница времени поступления последних кадров на host.

## Replay и проверки

Проверка реального приёма без окна, с теми же настройками и адаптером:

```powershell
.venv\Scripts\python.exe scripts\noitom_comparison\main.py --probe-seconds 10 --probe-output output\noitom_probe.json
```

Отчёт содержит число и частоту кадров, разрывы индексов, количество суставов,
результат преобразования пяти сегментов, версию DLL и ошибки. Отсутствие кадров
или ошибка даёт ненулевой код завершения. Освободите порт от другого экземпляра
Noitom-приёмника перед проверкой; обычный ESP32 viewer может работать параллельно.

Воспроизведение сохранённых segment orientations, без SDK и оборудования:

```powershell
.venv\Scripts\python.exe scripts\noitom_comparison\main.py --replay "recordings\<session>"
```

Replay сливает независимые потоки по relative timestamps, не по индексу.
Сначала показывается исходная собственная поза; Noitom появляется после первого
его сохранённого кадра. Кнопка позволяет воспроизвести сессию повторно.

```powershell
.venv\Scripts\python.exe -m pytest
$env:QT_QPA_PLATFORM = "offscreen"
.venv\Scripts\python.exe -m pytest -m "gui and not hardware"
```

Тесты проверяют математику адаптера, две модели, T0, отложенную обработку после
STOP, разные частоты/индексы, многократную запись, ошибки диска, fake-клиент,
loopback UDP и независимое отключение. Тест локальной DLL без костюма проверяет
загрузку, интерфейсы, настройку и повторные Open/Close; без библиотеки он
пропускается. Настоящий поток Axis Studio проверен на UDP 7012 с DLL из demo:
приём, 59 суставов, преобразование пяти сегментов, отрисовка и запись сессии.
При проверке 05.10.2026 окно записало 3026 кадров за 30.265 с (99.98 Гц),
повторная сессия — 311 кадров за 3.11 с (100 Гц), без разрывов SDK индексов и
ошибок преобразования. Повторный Start/Stop также проверен. Тест изолированно
проверял Noitom: ESP32 оставался в другом viewer, поэтому эти диагностические
сессии корректно имеют статус `incomplete` только из-за отсутствия own-потока.
Отчёт текущей проверки: `output/noitom_gui_live_report.json`.
Физическое согласование heading/поз двух костюмов и поведение при потере связи
с самим костюмом требуют отдельной аппаратной приёмки.
