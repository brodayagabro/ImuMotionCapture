# Тест направления тяжести MPU6050

Этот стенд отделяет три возможных источника ошибки:

1. сырые показания акселерометра;
2. оценку положения внутри DMP;
3. визуализацию и последующую обработку на компьютере.

Стендовая прошивка намеренно устанавливает нулевые аппаратные смещения
акселерометра и гироскопа. Она ничего не калибрует при старте и не записывает
NVS, поэтому шестипозиционный тест показывает собственные ошибки модулей.

## Подготовка прошивки

Скопируйте пример настроек Wi-Fi:

```bash
cp tools/benchmarks/mpu_gravity/firmware/mpu_gravity_benchmark/wifi_secrets.example.h \
  tools/benchmarks/mpu_gravity/firmware/mpu_gravity_benchmark/wifi_secrets.h
```

Заполните `WIFI_SSID` и `WIFI_PASSWORD`, затем прошейте ESP32 скетчем
`firmware/mpu_gravity_benchmark/mpu_gravity_benchmark.ino`.

Используются те же подключения, что и в основной системе: ESP32, TCA9548A и
MPU6050 с адресом `0x68`. Прошивка ищет TCA9548A на адресах
`0x70...0x77` и до пяти датчиков на его каналах. Нужны библиотеки:

- ESP32 Arduino core;
- AsyncUDP из ESP32 Arduino core;
- I2Cdevlib;
- MPU6050 с `MPU6050_6Axis_MotionApps20.h`.

IP-адрес контроллера печатается в Serial Monitor на скорости 115200.
Загрузка DMP выполняется на 100 кГц для устойчивой работы длинной шины через
TCA9548A; после инициализации поток переключается на 400 кГц.
Эта DMP-версия стенда принимает ответы `0x68`, `0x70`, `0x71` и
`0x73` только для диагностики совместимости. Значение `0x70` соответствует
MPU-6500: загружать в него MPU6050 MotionApps как рабочее решение нельзя.
Для проверки сырых данных MPU-6500 используйте
`firmware/mpu6500_raw_benchmark`.

## Запуск теста

Основная программа захвата и cube viewer не должны одновременно обращаться к
этому ESP32: стендовая прошивка отправляет поток последнему UDP-клиенту.

```bash
python3 tools/benchmarks/mpu_gravity/capture_gravity.py 192.168.1.117
```

По умолчанию сервер записывает каждое положение 12 секунд. Более короткий
пробный запуск:

```bash
python3 tools/benchmarks/mpu_gravity/capture_gravity.py 192.168.1.117 \
  --duration 5 --settle 1
```

Сервер последовательно запросит шесть положений: `+Z`, `-Z`, `+X`,
`-X`, `+Y`, `-Y`. Обозначение `+Z` означает, что стрелка положительной
оси Z на плате направлена вверх. Все подключённые датчики можно укладывать
одинаково и измерять одновременно. Во время каждой записи датчики, стол и
провода должны оставаться неподвижными.

Результат сохраняется в
`tools/benchmarks/mpu_gravity/results/<дата-время>/`:

- `raw_samples.csv` — все исходные accel/gyro и кватернионы;
- `summary.json` — рассчитанные показатели и статусы отдельных проверок;
- `report.md` — краткий человекочитаемый отчёт.

CSV перезаписывается после каждой завершённой грани, поэтому уже собранные
данные сохранятся и при досрочной остановке.

## Как читать результат

- Большая ошибка направления или модуля сырого ускорения указывает на
  смещение/масштаб акселерометра, питание, монтаж либо конкретный MPU6050.
- Сырое ускорение правильное, но велики `DMP↔accel` или `Дрейф g DMP` —
  проблема находится в DMP, гироскопе или прошивке, а не в отрисовке кубика.
- Оба набора проверок проходят, но рабочий аватар всё ещё движется — следует
  проверять рабочий UDP-протокол, перестановку осей, калибровку сегментов и
  сглаживание на стороне приложения.

Оценки `bias_counts` и `scale_counts_per_g` в отчёте предназначены для
диагностики. Их нельзя напрямую записывать в регистры offset MPU6050 без
учёта формата и шага этих регистров.

Полный `quaternion_drift_deg` также остаётся в JSON, но не влияет на PASS:
у MPU6050 нет магнитометра, поэтому поворот вокруг вертикали наблюдать нечем.
На результат влияет именно дрейф рассчитанного DMP направления тяжести.

После теста верните на ESP32 рабочую прошивку, соответствующую
`WHO_AM_I`: `sensors/esp32/DMP_with_TCA9548A_udp/` для `0x68` либо
`sensors/esp32/MPU6500_with_TCA9548A_udp/` для `0x70`.
